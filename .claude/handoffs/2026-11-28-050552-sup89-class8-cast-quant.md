## Architecture (verified)

- Op-name -> kind map: `classifyOperation()` in `lib/IR/ANEOperationGraph.mm` (~line 4). `cast` is
  absent -> `ANEOperationKindUnsupported`. `quantize`/`dequantize`/`constexpr_affine_dequantize`
  already map to `ANEOperationKindQuantize`/`Dequantize`.
- Legalize: `lib/Transform/ANEH16GLegalizePass.mm`. Line ~122 emits the unsupported-op error when
  `![target supportsOperationKind:node.kind]` (H16GTarget.mm:433 allows Constant/Conv/Matmul/ALU/
  LUT/Reduce/Layout/Quantize/Dequantize/HighLevel?/Mask — check exact list). Line ~137-139 folds ALL
  Quantize/Dequantize nodes via `markFoldedIntoNumericBoundary`.
- Fold consumption: `lib/Planning/ANETaskScheduler.mm:356` skips folded nodes when building `active`;
  `effectiveProducer` (line ~27) resolves through folded nodes; `quantizedOutput` (~line 32) marks a
  result surface `ANEElementTypeInt8` when its users include a `quantize` node — the int8-surface
  machinery exists at the *consumer* side, not for a standalone quantize node's own output.
- Conv boundary folding is conditional elsewhere: `numericModeForConv` (legalize ~line 96) picks
  W8A8InputBoundary/W8A8Packed/W8A8OutputBoundary from quantize/dequantize adjacency. So the fold is
  *meant* for conv boundaries but the mark is applied unconditionally -> standalone nodes vanish.
- Task model: `taskCapabilityRows()` in `plugins/H16G/H16GTarget.mm:126` is a whitelist of
  (stageOperations, inputShapes, outputShape, numericMode, outputStorage) -> H16GTaskCapability with
  `packetFamily` + `geometry` + programTaskCount/semanticConstraint. A non-folded quantize node would
  go active -> stage -> group -> `taskCapabilityForStageOperations:` -> NO row exists -> nil ->
  presumably assembler refusal. New rows needed for standalone quant/dequant.
- Packet families (`plugins/H16G/H16GTarget.h:15`): SquareMatmul, UnaryLUT, ScalarScale,
  MatrixRowALU, RowStateALU, Reduction, MatrixRowDivision, SquareALU, PrimitiveFallback. No
  conversion/copy family. `PrimitiveFallback` is the generic escape — TaskEncoder.mm:152 handles it.
- Surface element types DO flow through: `H16GProgramAssembler.mm:22` maps ANEElementTypeInt8;
  `elementBytes()` exists; `physicalLayout(shape, elementType, ...)` — so an int8 surface on a real
  task is representable.
- Oracle corpus `research/oracles/h16/` has NO cast/quant/convert oracle — no decoded conversion
  program exists in evidence. Compiler policy per the error wording is "only emit decoded primitives".
- H13 also refuses (h13.unsupported-program / h13.unsupported-logical-result-conversion) — the test
  only exercises H16G.

## Open design question (the real work) — REFINED after encoder read

What legal .hwx program does a standalone cast/quantize/dequantize lower to?

Verified constraints (session 2):
- `PrimitiveFallback` is NOT usable standalone: `H16GTaskEncoder.mm:152` errors
  "compound task requires standalone primitive fallback" — it only exists inside compositions.
- Element types live in the PACKAGE surfaces, not the TD program bytes — programs are fixed
  templates (e.g. ALU ops patch only the opcode at `selectorOffset`). So conversion happens at the
  surface-read/write datapath: an identity-ish elementwise program + differently-typed output
  surface IS the decoded conversion mechanism (same model as the int8 numeric-boundary fold).
- Element types already plumbed end-to-end: `ANEElementType` has FP16/FP32/Int8/Int32/UInt64/Bool
  (`lib/IR/ANEGraphIR.h:7`); `elementBytes()` handles all of them in the assembler.
- BUT geometry envelopes are narrow: `H16GALUEncoder` square only {128,256,512,1024,2048} fp16,
  opcodes add/mul/max/min ONLY (binary, 2-input). Test shapes are [1,64,64], [1,375,375],
  [1,64,64,64] — none fit SquareALU. UnaryLUT rows are image @[1,1,size,size] for size in {128,256}.
  BroadcastALU = matrix-row; MatrixRowDivision needs row-vector operand.
- CRITICAL reframe from H13: `ANEH13Compiler.mm:2900` refuses non-fp16/non-bool function RESULTS —
  "H13 logical result conversions require explicit hardware or GPU coverage". Bool results ARE
  allowed. This suggests upstream Apple practice: dtype-converting package boundaries go to GPU/CPU,
  not ANE — except int8 quant boundaries and bool. The class-8 test still demands real H16G
  artifacts for all 5 cast directions + standalone quant/dequant though.
- No `ANEOperationKindCast` exists; adding one requires touching the enum, kindName, supports lists.

Plausible fix shapes, in order of preference:
A. NEW packet family (e.g. BoundaryConversion) + encoder emitting a decoded pass-through/identity
   program with in/out surfaces of differing element types. Blocker: identity/copy program must
   exist in decoded H16G corpus — CHECK `H16GSRAMChainEncoder`/`H16GConstantPacker`/layout encoders
   for a copy/move TD form first (SRAM bridge tasks may BE copies — `ANEScheduledBridgeStorageSRAM`
   tasks at assembler ~641-680 encode pass-throughs).
B. Rewrite `cast` in a transform pass into an existing geometry-fitting op whose program preserves
   values (e.g. `mul(x,1)` ScalarScale) — blocked by geometry: test shapes don't fit any envelope,
   so this also needs a new template anyway. Only viable if a tileable arbitrary-shape elementwise
   template exists (check BroadcastALU rows/cols coverage of 64x64 / 375x375).
C. If no decoded conversion/copy form exists for H16G at all: the honest PR is compiler plumbing
   that produces a REAL refusal diagnostic naming the missing primitive + doc, not a fake lowering —
   BUT the test demands rc=0 + artifacts, so verify (A) exists before settling.
- standalone quant/dequant: the same conversion-task question, PLUS the fold must be guarded so
  boundary nodes survive (markFolded only when a conv numeric boundary absorbs the node).

## Session-3 verdict on the encoder landscape (decisive)

- `H16GSRAMChainEncoder` is 128x128-only composed compute pairs (`taskFormPlan`) — NOT a copy path.
- The w8a8 fixture's actual emission proves the fold model: `x` binding is a plain fp16 surface
  (524288 B), output `c3` fp16; the quantize/dequantize produce NO standalone records — conversion
  lives inside the conv task's numeric-mode read/write path. There is no decoded standalone
  conversion/copy/identity TD form anywhere in H16G (checked ALU, LUT, SRAM chain, layout, broadcast
  families — all fixed-envelope fp16 compute).

  (a) mint an oracle for standalone quantize/cast on real Apple ANE — needs a macOS host (this lane's
      host is Linux; `research/mint_oracles.py` is the minting tool — check its host requirements);

      encoder already writes conversion-bearing task forms; a minimal standalone form may be a
      sub-record of it). Feasible but real RE work — several hours.
