# MIL-to-HWX Compiler Design

Status: v1 exact-pattern prototype; retained as a hardware oracle  
Target: Apple M4 H16G  
Implementation: Objective-C public API with an Objective-C++ compiler core

This document describes the first prototype. It is not the architecture of the
generic staged compiler. The replacement design is
`GENERIC_STAGED_HWX_COMPILER_DESIGN.md`. In particular, the v1 semantic-pattern
selection, recovered descriptor rows, and skeleton patching are evidence tools,
not production compiler stages.

## Goal

Build a standalone compiler that reads real MIL text, constructs typed compiler
IR, applies explicit transformations, and emits H16G HWX programs. The first
release must compile and execute the three workloads used to investigate the
Apple compiler:

1. fp16 Conv1x1 followed by ReLU at NCHW `[1,64,64,64]`;
2. four-head attention with sequence length 64 and head width 64;
3. four Conv1x1 layers at `[1,64,64,64]` with int8 weights and int8
   inter-layer activations.

Success requires element-wise comparison against an independent CPU reference
on an M4. Producing parseable HWX or matching a compiler-generated byte string
alone is insufficient.

## Non-negotiable properties

- MIL is parsed by a lexer and grammar-driven parser. Operation semantics are
  never recovered with regular expressions.
- Every IR value has a type, shape, definition and source location.
- Transformations run as named passes with verifiers before and after lowering.
- Pattern selection is semantic. Shape alone cannot select a fused program.
- Unsupported input fails with a diagnostic. There is no silent fallback.
- H16G facts live in one target description with evidence and availability.
- Emission is deterministic.
- Existing Stage 1 leaves may serve as verified encoders behind typed adapters.
  Their flat request structure is not exposed as compiler IR.
- An opaque compiler-minted program may be used as a differential oracle. It
  may not be returned as the result of compilation.

## Compilation model

```text
MIL text
  -> tokens and syntax tree
  -> typed Graph IR
  -> canonical Graph IR
  -> ANE Primitive IR
  -> H16G Machine IR
  -> HWX object and binding manifest
```

### MIL syntax layer

The lexer recognizes identifiers, integer and floating-point literals, string
literals, punctuation, comments and end-of-file. Every token records byte,
line and column ranges.

The parser supports the structural MIL forms required by the three fixtures:

- `program`, build attributes, functions and returns;
- scalar and tensor types;
- operation result declarations;
- named operation arguments and bracket attributes;
- scalar, inline tensor and BLOBFILE constants;
- tuple-valued arguments used by concat when it is later added.

The syntax tree preserves spellings and source locations. Semantic resolution
turns names into value identities and validates single assignment.

### Graph IR

Graph IR is frontend-neutral SSA. Values carry `ANETensorType`; operations use
typed attribute records. The initial operation set is:

- Input and Constant;
- Conv2D, Relu, Matmul, Multiply and Softmax;
- SliceBySize, Transpose and Reshape;
- Quantize, Dequantize and AffineDequantize;
- Return.

Constant values distinguish scalar, inline tensor and external blob slices.
External slices contain path, byte offset, logical type and logical shape.

### Pass manager

The implemented v1 driver has three explicit IR-to-IR passes after frontend
construction and verification:

1. `ane.select-semantic-pattern` (Graph IR to Primitive IR)
2. `h16g.lower-machine` (Primitive IR to H16G Machine IR)
3. `h16g.emit-hwx` (Machine IR to executable artifact)

The grammar frontend performs tokenization, syntax construction, name
resolution, type import and Graph IR verification before the pass manager.
Each semantic plugin owns the exact canonical law it accepts and declines
near-misses. This keeps the first implementation honest: it does not report
unimplemented canonicalization or optimization stages as passes.

The intended finer-grained expansion as support grows is:

1. `resolve-values`
2. `infer-and-verify-types`
3. `canonicalize-constants`
4. `canonicalize-layouts`
5. `collapse-quant-dequant`
6. `fuse-conv-relu`
7. `recognize-attention`
8. `recognize-w8a8-chain`
9. `legalize-ane-primitives`
10. `select-h16g-patterns`
11. `schedule-h16g-tasks`
12. `plan-h16g-memory`
13. `emit-hwx`
14. `verify-hwx`

Every implemented pass has a stable identifier and declares its input and
output IR level. Verifiers run on both sides of each transition. Future items
in the longer list become independent passes only when they perform an actual
transformation.

### ANE Primitive IR

Primitive IR contains typed operations such as `ANEConv`, `ANEMatmul`,
`ANESoftmax`, `ANELayoutTransform`, `ANEQuantizedConv` and `ANEFusedRegion`.
It contains no descriptor offsets or raw mode words.

The three initial region laws are:

```text
conv_relu:
  y = relu(conv1x1(x, W))

attention_h4_s64_d64:
  q, k, v = slices(x)
  scores = matmul(transpose(q), transpose(k)) * 0.125
  probabilities = softmax(scores, axis=-1)
  y = transpose(matmul(probabilities, transpose(v)))

w8a8_conv_chain_4:
  c0 = conv1x1(x, dequant(W0))
  c1 = conv1x1(dequant(quant(c0)), dequant(W1))
  c2 = conv1x1(dequant(quant(c1)), dequant(W2))
  y  = conv1x1(dequant(quant(c2)), dequant(W3))
```

The recognizers check operation order, dataflow, constants, axes, layouts,
dtypes, scales, zero points and shapes. A partially matching graph remains
unfused and will fail later if no legal primitive implementation exists.

### H16G Machine IR

Machine IR models surfaces, constant regions, tasks, dependencies, DMA
transfers, compute commands, waits, SRAM allocations and output bindings.
Unknown descriptor fields remain in the H16G encoder and carry an evidence
annotation. Generic optimization passes never inspect opaque fields.

The machine scheduler must express the observed boundary behavior of W8A8:
the first task accepts fp16 input, middle tasks use int8 activation transfer and
dual-pack compute state, and the final task writes fp16 output.

### Plugins

The first release uses static registration with these internal protocols:

- frontend plugin;
- pass provider;
- semantic pattern;
- target description;
- machine lowering;
- HWX emitter;
- verifier.

Plugins publish identifiers, versions, capabilities, constraints and explicit
priorities. Equal-priority matches are an error. A stable C ABI for dynamic
bundles can be added after the in-process contracts settle.

### Stage 1 boundary

Stage 1 remains a hardware leaf library. Each adapter receives a typed Machine
IR operation and translates it to a leaf-specific request. Adapters verify the
complete binding and semantic contract before calling the leaf.

Any embedded HWX skeleton is private to its encoder. The compiler still has to
derive the selected pattern, constants, bindings and execution plan from MIL.
The target state is structured TD and container construction for all three
patterns.

## Public interface

```objc
@interface ANECompiler : NSObject
- (nullable ANEExecutableBundle *)compileMILData:(NSData *)milData
                                      modelRoot:(NSURL *)modelRoot
                                         target:(NSString *)target
                                    diagnostics:(ANEDiagnosticEngine *)diagnostics;
@end
```

`ANEExecutableBundle` owns one or more HWX images, their binding manifests and
an ordered dispatch plan. The first Conv+ReLU milestone emits one image. The
attention and W8A8 milestones may contain multiple images until their fused
multi-TD encoders are complete, but every dispatched image must be produced by
this compiler and every intermediate binding must be explicit in the bundle.

## Verification gates

Each milestone must pass:

1. lexer and parser negative tests;
2. parse-print-parse equivalence;
3. Graph IR type and use-def verification;
4. pass-specific before/after golden tests;
5. deterministic HWX emission;
6. HWX container and descriptor structural verification;
7. differential structural comparison with an Apple-compiled oracle;
8. two warm hardware executions on M4;
9. element-wise output comparison with an independent CPU implementation.

Performance is recorded only after correctness. Apple compiler output is never
called from the production compiler or runtime.
