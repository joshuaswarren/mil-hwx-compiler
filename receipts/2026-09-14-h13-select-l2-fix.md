# H13 select: the scratch arena, not the first L2 tile (2026-09-14)

Host-only compiler work. No ANE, no SSH, no `ane-linux-experiments`, no jwm1
from this slice; the device numbers below are quoted from `IslandsExecJwm1`'s
single guarded submit on jwm1-linux.

Executing model: `anthropic/claude-opus-5` as reported by the session's own
workstation block. The assigned route for this slice is `openai-codex/*`, so
this is a routing discrepancy and is reported rather than hidden; every
measurement below is host-reproducible from the commands given.

**If you rebuild a bundle over this fix, re-stamp the manifest.** The ANEC
header's channel-3 tile count is what the device honours, and
`load_bundle` requires `programs[].scratch_bytes` to equal it exactly, with
no rounding. A new anec against a stale manifest is refused before the
device is touched, so the fix presents as a broken bundle rather than as a
fixed one. For this program the pair is 417 tiles and 6832128 bytes.

## Verdict

`h13.select-first-l2-tile` is retracted. It was never an L2 tiling or stride
question, and the earlier receipt's "do not patch L2, this needs a new
capture" verdict was right about the L2 words and wrong about the defect.

The 375-wide select blends through channel 3, the scratch surface, and Apple
uses channel 3 as an **arena with three stages**, not one surface:

| stage | scratch offset | row | span |
| --- | ---: | ---: | ---: |
| cond-false (`b`) half, head-interleaved | 0 | 6016 | 2256000 |
| cond expanded to fp16 | 2256000 | 768 | 2304000 |
| cond-true (`a`) half, head-interleaved | 4560000 | 6016 | 2256000 |

The program therefore touches **6816000** scratch bytes. `encodeBooleanOp`
sized channel 3 as `program.output.allocationBytes` = **2310144** on the
written assumption that "the scratch staging moves operand/result data, so it
never exceeds one surface". It does exceed it, by 3x: task 3's write of the
cond-true half and task 4's read of it both ran 4.5 MB past the end of the
surface the ANEC header declares.

Row 6016 is `8 * 752`: the halves are head-interleaved, 376 fp16 lanes per
head for 375 valid, which is why the corruption mask is bit-identical across
all 8 heads.

## The number is Apple's, not a guess

Apple lays its `__DATA/__bss` scratch at `0x30000000`, below every resource
address. For `select_rrb_1x8x375x375` the lowest resource is `0x30684000`, so
Apple's own scratch allocation is `0x684000` = **6832128** = 417 tiles =
`align(6816000, 0x4000)`.

Deriving the extent from the channel-3 tile-DMA descriptors — the highest
`base + depth` any task's channel-3 slot reaches — reproduces that gap on
every decoded boolean capture:

```text
select_rrb_1x8x375x375           derived 6816000  aligned 6832128  apple gap 6832128
select_ninf_bool_1x8x375x375     derived 6816000  aligned 6832128  apple gap 6832128
floor_div_native_1x64x1x1_rr     derived     128  aligned    16384  apple gap    16384
floor_div_native_1x64x1x1_s2     derived     128  aligned    16384  apple gap    16384
floor_div_comp_1x64x1x1_rr       derived     128  aligned    16384  apple gap    16384
floor_div_comp_1x64x1x1_s2       derived     128  aligned    16384  apple gap    16384
less_bool_cast_1x375             derived     384  aligned    16384  apple gap    16384
select_rrb_1x64x1x1              derived       0  aligned        0  apple gap        0
floor_r_*, less_bool_rr_*, floor_div_native_1_*, floor_b_1_idx   derived 0, apple gap 0
```

20 of 20, zero-scratch captures included. The `{64,1,1}` select selects no
channel-3 slot at all — every intermediate stays L2-resident — which is why
that shape was already bit-exact and hid this completely.

Widening the same check past the boolean family, over every capture in
`research/oracles/h13/` that carries both task descriptors and resource
addresses: **1452 captures, 346 of them scratch-using, 1451 exact against
Apple's gap, 0 under-estimates, 1 over-estimate.**

The single over-estimate is `sched_fused_lut_d512_s512`, derived 3670016
against Apple's 2621440. Its channel-3 stages deliberately overlap — four
destination bases (2097152, 1572864, 786432, 0) all carrying the full
surface depth 2097152, a sliding window into one region rather than four
regions — so `base + depth` counts the window's depth from its own offset
and lands 1 MB high. That is the shape of the derivation's error: it is
exact when stages are disjoint, as the boolean arena's are, and high when
they are staggered views of one region. It is never low, anywhere in the
corpus, which is the direction that matters for a DMA bound.

## Why the device answer looks the way it does

Island B's cond is uniformly false, `a` is an all-`0xFC00` fill and `b` is a
real score matrix, so a correct select is a pure passthrough of `b`, and
`y = a_half + b_half` with `a_half` all zeros. Read out of range, `a_half`
returns live fp16 instead of zeros, so the device writes `b[lane] + x`:

- no `-inf`, because `a` is never selected (device inf count 0);
- in-distribution magnitudes, not bit garbage, and not fp16 neighbours of the
  reference, because the lane is a **sum** of two in-band values;
- never equal to `b` at the same position in another head;
- independent of cond content, which is what `IslandsExecJwm1` measured.

Corroborating arithmetic for the row window: the emitted scratch tail past
the `b` half is `2310144 - 2256000` = 54144 bytes = exactly **9.0**
interleaved rows of 6016. The device showed corruption in H rows 0-8 and
nothing at row 9 or above. The exact aliasing of the out-of-range access is
the driver's mapping, not this compiler's, and is not claimed here.

## Who sizes channel 3

`libane` does, from the ANEC header, not from the manifest. In the pinned
checkout `f261a6cb`, `ane_chan_init` (`libane/ane.c:191-198`) loops every
`bdx` and takes `bo->size = tile_shift(anec->tiles[bdx])` with
`TILE_SHIFT 0xE`, so channel 3 becomes `417 << 14` = 6832128 bytes. The
worker only sends and reads the bound tensor channels 4..7 and never sizes
channel 3 itself. The manifest's `programs[].scratch_bytes` is the loader's
exact-equality gate (`bundle.cpp:318-319`, corroborated independently on the
`a9f14124` build's `validate_program_contract`). So the two-byte header
change is the entire device-side fix, and the manifest stamp is what decides
whether the pair loads at all. Mechanism and file references from
`IslandsExecJwm1`; an earlier draft of this receipt had the two backwards.

## Cross-host corroboration

- `IslandsExecJw16` (`dd976b49`): its `island-select-8head` declares the same
  2310144. Its other two islands, `island-attn-a-kt` and `island-pv`, declare
  `scratch_bytes` 0 for every program and both returned clean to fp16
  rounding — the one island with a channel-3 arena is the one that corrupted.
  Its exhaustive search for a constant clobber displacement into any staged
  tensor, dense and at the 384-element row pitch, found nothing consistent
  across even 6 corrupted lanes while the values stayed in-distribution,
  which is what a read landing past a surface looks like and what a wrong
  source tensor does not. It has marked its `ANE_EXEC_VALUE_MISMATCH` verdict
  provisional pending the re-run, which has now returned zero.
- The jw16/jwm1 disagreement on which late rows start a period late was
  consistent with this cause but never predicted by it, and is retired by the
  zero rather than explained: the landing zone past the declared surface
  depends on what the driver placed after it, which differs per host and per
  run, and after the fix there is no landing zone. The arena model fixes the window (the 54144-
  byte tail, 9.0 interleaved rows) and the per-head identity (the halves are
  head-interleaved at 752 bytes, so one byte window covers the same lane
  offsets in every head). It does not explain the fine structure and is not
  claimed to.
- `EncoderParityAne`: its 48 accepted submits contain no select, so they are
  unaffected, though both its bundles were built by the pre-fix `83d486b1`.

## Coverage gaps

- No case with a true cond lane has run on either device. Every authenticated
  capture's `encoder_input_mask` is all ones, so the golden clips give a
  uniformly false cond and the `-inf` fill is never selected. This fix is
  content-independent — the arena and its extent do not depend on cond — but
  the cond-true path stays unexercised on hardware. A padded-frame clip is
  the case still uncovered.
- `select_ninf_bool_1x8x375x375` derives the same 6816000 and stays rejected
  at the MIL gate for the unrelated reason recorded in
  `2026-09-13-h13-select-envelope.md`; nothing here opens it.
- mlx-omarchy `receipts/2026-09-14-encoder-split-plan.md` carries this
  island's scratch footprint as 2310144 and is now stale.
