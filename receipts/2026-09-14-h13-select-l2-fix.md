# H13 select: the scratch arena, not the first L2 tile (2026-09-14)

Host-only compiler work. No ANE, no SSH, no `ane-linux-experiments`, no jwm1.

Executing model: `anthropic/claude-opus-5` as reported by the session's own
workstation block. The assigned route for this slice is `openai-codex/*`, so
this is a routing discrepancy and is reported rather than hidden; every
measurement below is host-reproducible from the commands given.

## Verdict

`h13.select-first-l2-tile` is retracted. It was never an L2 tiling or stride
question, and the earlier receipt's "do not patch L2, this needs a new
capture" verdict was right about the L2 words and wrong about the defect.

The 375-wide select blends through channel 3, the scratch surface, and Apple
uses channel 3 as an **arena with three stages**, not one surface:

| stage | scratch offset | row | span |
| --- | ---: | ---: | ---: |
| cond-false (`b`) half, head-interleaved | 0 | 6016 | 2256000 |
| cond expanded to fp16 | 2256000 | 768 | 2304000 |
| cond-true (`a`) half, head-interleaved | 4560000 | 6016 | 2256000 |

The program therefore touches **6816000** scratch bytes. `encodeBooleanOp`
sized channel 3 as `program.output.allocationBytes` = **2310144** on the
written assumption that "the scratch staging moves operand/result data, so it
never exceeds one surface". It does exceed it, by 3x: task 3's write of the
cond-true half and task 4's read of it both ran 4.5 MB past the end of the
surface the ANEC header declares.

Row 6016 is `8 * 752`: the halves are head-interleaved, 376 fp16 lanes per
head for 375 valid, which is why the corruption mask is bit-identical across
all 8 heads.

## The number is Apple's, not a guess

Apple lays its `__DATA/__bss` scratch at `0x30000000`, below every resource
address. For `select_rrb_1x8x375x375` the lowest resource is `0x30684000`, so
Apple's own scratch allocation is `0x684000` = **6832128** = 417 tiles =
`align(6816000, 0x4000)`.

Deriving the extent from the channel-3 tile-DMA descriptors — the highest
`base + depth` any task's channel-3 slot reaches — reproduces that gap on
every decoded boolean capture:

```text

select_ninf_bool_1x8x375x375     derived 6816000  aligned 6832128  apple gap 6832128
floor_div_native_1x64x1x1_rr     derived     128  aligned    16384  apple gap    16384
floor_div_native_1x64x1x1_s2     derived     128  aligned    16384  apple gap    16384
floor_div_comp_1x64x1x1_rr       derived     128  aligned    16384  apple gap    16384
floor_div_comp_1x64x1x1_s2       derived     128  aligned    16384  apple gap    16384
```

20 of 20, zero-scratch captures included. The `{64,1,1}` select selects no
channel-3 slot at all — every intermediate stays L2-resident — which is why
that shape was already bit-exact and hid this completely.

## Why the device answer looks the way it does

Island B's cond is uniformly false, `a` is an all-`0xFC00` fill and `b` is a
real score matrix, so a correct select is a pure passthrough of `b`, and
`y = a_half + b_half` with `a_half` all zeros. Read out of range, `a_half`
returns live fp16 instead of zeros, so the device writes `b[lane] + x`:

- no `-inf`, because `a` is never selected (device inf count 0);
- in-distribution magnitudes, not bit garbage, and not fp16 neighbours of the
  reference, because the lane is a **sum** of two in-band values;
- never equal to `b` at the same position in another head;
- independent of cond content, which is what `IslandsExecJwm1` measured.

Corroborating arithmetic for the row window: the emitted scratch tail past
the `b` half is `2310144 - 2256000` = 54144 bytes = exactly **9.0**
interleaved rows of 6016. The device showed corruption in H rows 0-8 and
nothing at row 9 or above. The exact aliasing of the out-of-range access is
the driver's mapping, not this compiler's, and is not claimed here.

## Change

`plugins/H13/H13Program.cpp`

- `findH13Register` / `h13RegisterOffset`: the register-record walker moved up
  into the first anonymous namespace and split so absence is a return value,
  not a chain diagnostic. The duplicate walker at the bottom of the file is
  gone — one walker, three call sites.
- `taskScratchExtent`: the highest scratch byte one task's channel-3
  descriptors reach, over the three selector fields `bindTasks` rebinds
  (source 0 `0x13808`/`0x13814`, source 1 `0x1381c`/`0x13828`, destination
  `0x17804`/`0x17810`).
- `encodeBooleanOp`: `scratchAllocationBytes = alignTile(scratchExtent)`.
  Selecting channel 3 with no descriptor to size it now throws instead of
  emitting an unbacked surface.

`research/inspect_anec.py`

- `check_layout` passes the binding's `dtype` to `surface_layout`, whose
  `bool_elements` parameter existed and was never passed. Without it any
  select package failed validation on the cond binding's 384-byte row, so no
  select package could be validated at all. Now it validates.

`tests/test_h13_boolean_cli.py`

- `apple_scratch_bytes(record)`: Apple's `__DATA/__bss` gap from the capture.
- Every implementable capture and every const twin asserts emitted
  `scratchBytes == apple_scratch_bytes(record)`.
- `assert_select_375_scratch`: the encoder-shaped `[1, 8, 375, 375]`
  regression. Locks all five tasks selecting channel 3, the three arena
  stages (`0x17804`/`0x17810` = 2256000/2304000, 0/2256000, 4560000/2256000
  and task 4's `0x13808`/`0x13814` = 4560000/2256000), `tiles[3] == 417`, and
  `scratchBytes == 6832128 == apple_scratch_bytes`.
- Both select captures now run `validate()`.

The two anecs differ at byte offsets 52-53 and nowhere else; `anec[0x1000:]`
is byte-identical, so the task stream, the constant section and every surface
layout are unchanged. The fixed island payload is at
`/var/tmp/SelectL2Fix/island-select-8head-program-0.anec`, and the bundle
manifest needs `programs[0].scratch_bytes` 2310144 -> 6832128 or the worker
will not allocate it.

## Verification

```text
make test-h13
# 15 CLI suites PASS, 144 s

python3 tests/test_h13_boolean_cli.py build/mil-hwxc
# h13 boolean cli: PASS

python3 research/inspect_anec.py <select_rrb_1x8x375x375 package>
# rc 0   (before this change: "ANEC package error: incorrect physical layout")
```

The regression is proved to bite: reverting only
`program.scratchAllocationBytes = alignTile(scratchExtent)` to
`= program.output.allocationBytes` and rebuilding fails the suite at
`test_h13_boolean_cli.py:246 AssertionError: select_rrb_1x8x375x375`. The
line was restored and the suite re-run green.

Byte-exactness against the captures is unchanged: the scratch size lives in
the ANEC header's channel-3 tile count, not in the task stream the captures
pin.

## Device verification

Outstanding, and it is the acceptance evidence this receipt does not carry.
Pre-fix device state, from `IslandsExecJwm1`'s
`receipts/2026-09-14-encoder-islands-exec-jwm1-linux.json`: 10728 wrong lanes
total, 1341 per head, mask bit-identical across heads, H rows 0-8 only,
nothing at row 9 or above, against
`B_ref_attention_mask_9.bin` sha256
`9ceed6167044e086fc667505117163bbdb54ff4fe23cd3133bbfba39190fc15c`.
Expected after: 0. One guarded submit, deadline 10 s, one iteration, no
retry, stop on -110.

The bundle manifest must carry the new `scratch_bytes`. The ANEC header's
channel-3 tile count and the manifest's `programs[0].scratch_bytes` are read
by different consumers: shipping the fixed anec with the manifest still
saying 2310144 leaves the worker allocating 141 tiles and the defect intact.
`417 * 0x4000 = 6832128`, so the fixed pair is self-consistent.

No wrong-lane count is claimed here for the fixed bundle. Nothing in this
receipt was executed on hardware.
